# /verify

Live UAT execution from the user's perspective. Opens the running app in Chrome, walks through each acceptance criterion, judges visual quality, and escalates failures.

> **Principle:** A feature isn't done until a real human (or an agent acting like one) confirms it works and looks right.

## Usage

```bash
/verify               # Auto-detect from current branch
```

## What Makes This Different

| `/review-all` | `/verify` |
|--------------|-----------|
| Code, design, UX static analysis | Live browser interaction |
| Developer perspective | User perspective |
| "Is the code correct?" | "Does it feel right?" |
| Reads files | Opens the actual app |
| Fast (no browser) | Thorough (browser + screenshots) |

Use `/review-all` to catch code problems. Use `/verify` to confirm the shipped feature actually works from the user's point of view.

## Execution Steps

### Step 1: Find the Spec

If argument given (e.g., `p273`):
```bash
find features -name "*p273*" -not -path "*/archive/*" 2>/dev/null
```

If no argument, infer from branch:
```bash
git branch --show-current  # e.g., feature/p273-verification-gate → p273
```

Read the spec file completely. Also check for a UAT file:
```bash
# UAT file (if generated by /generate-tests)
ls features/uat/p{N}.md 2>/dev/null
```

If UAT file exists → **use it as the primary verification plan** (it has structured scenarios).
If not → derive scenarios from the spec's "Acceptance Criteria" section.

---

### Step 2: Build Verification Plan

Parse the UAT file (or acceptance criteria) into a structured list:

```
Verification plan for P{N}: {Title}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Scenarios to run: {N}
Pages to visit: {list}
User states needed: {verified / unverified / anonymous / etc.}
Estimated time: ~{N} min

Scenarios:
  [A] {scenario-id}: {short description} — needs: {user state}
  [B] {scenario-id}: {short description} — needs: {user state}
  ...
```

Announce the plan. If > 8 scenarios, ask: "That's {N} scenarios. Run all, or pick specific ones? (all / 1,3,5 / etc.)"

---

### Step 3: Pre-flight

Check the dev server is running:
```bash
curl -s http://localhost:5001 -o /dev/null -w "%{http_code}" 2>/dev/null
```

If not running (not 200):
```
Dev server not running at localhost:5001.
Start it with `npm run dev` then run /verify again.
```
Stop here. Don't proceed without a running app.

Announce: "Dev server confirmed at localhost:5001. Opening Chrome."

---

### Step 4: Open Chrome and Check Baseline

Use `mcp__claude-in-chrome__tabs_context_mcp` first to see current tabs.

Open a new tab to the app:
```
mcp__claude-in-chrome__navigate(url="http://localhost:5001")
```

Take a baseline screenshot. Assess:
- Does the page load (not blank, not 404)?
- Is the basic layout intact (header, nav, content area)?
- Any obvious console errors?

```
mcp__claude-in-chrome__read_console_messages(pattern="error|Error|TypeError|Uncaught")
```

If baseline fails (blank page, 404, console errors at load) → **stop and report**. Don't run scenarios on a broken app.

---

### Step 5: Run Scenarios

For each scenario in the verification plan:

#### 5a. Set Up User State

Before each scenario that needs a specific user state, check if the current session matches:

```
mcp__claude-in-chrome__javascript_tool(script="
  // Check current auth state
  const session = JSON.parse(localStorage.getItem('supabase-auth-token') || 'null');
  console.log('Current user:', session?.user?.email, 'verified:', session?.user?.user_metadata?.isVerified);
")
```

If the scenario needs a **different** user state than what's logged in, pause and tell the user:
```
Scenario UAT-{N}: needs {user state} (currently logged in as {state}).
Please {action — e.g., "log in as your test unverified account" / "log out" / "open an incognito tab"}.
Done? (press enter)
```

Wait for confirmation before continuing.

#### 5b. Navigate to the Right Page

Navigate to the URL relevant to the scenario. Example:
```
mcp__claude-in-chrome__navigate(url="http://localhost:5001/create")
```

Wait for the page to settle:
```
mcp__claude-in-chrome__wait_for(selector="[data-loaded]", timeout=3000)
```
(Fall back to a 1.5s wait if no data-loaded sentinel.)

#### 5c. Interact as the User Would

Perform the action described in the scenario — click buttons, fill forms, submit. Act like a real user, not a developer:

- Fill fields with **realistic content** (not "test", not "aaa") — use plausible values:
  - Story text: "Remote work improves team communication"
  - Names: realistic-sounding
- Click the expected CTA (Save, Submit, Agree, etc.)

Use these tools as needed:
- `mcp__claude-in-chrome__fill` — fill inputs
- `mcp__claude-in-chrome__click` — click buttons
- `mcp__claude-in-chrome__find` — find elements by text or selector

#### 5d. Capture & Assess

Immediately after the action:
```
mcp__claude-in-chrome__take_screenshot()
```

Check the result against the scenario's **Then** clause. Ask yourself:

1. **Functional:** Did the right thing happen? (toast appeared, navigation occurred, button changed state, etc.)
2. **Message accuracy:** Is the toast/error text exactly what the spec says? (copy matters)
3. **Visual quality:** Does it look clean? Right colors? Correct sizing? Nothing overflowing or misaligned?
4. **Common sense:** Would a first-time user understand this? Does the feedback make the next step obvious?

Check for unexpected console errors:
```
mcp__claude-in-chrome__read_console_messages(pattern="error|Error|Uncaught", limit=5)
```

#### 5e. Score the Scenario

```
UAT-{id}: {description}
  Result: ✅ Pass / ❌ Fail / ⚠️ Partial
  Notes: {what happened, verbatim if toast message}
  Screenshot: [taken]
```

Mark ❌ (not ⚠️) if:
- The expected outcome didn't happen at all
- The message text is wrong (even one word off from spec)
- The user would be confused about what to do next
- Console errors appeared during the interaction

Mark ⚠️ (partial) only if the core behavior works but something minor is off (e.g., slightly wrong color, small layout quirk).

---

### Step 6: Visual Quality Pass

After all functional scenarios, do one pass specifically for visual quality. This is about aesthetics and polish, not correctness.

Visit the main page(s) affected by this feature. Take screenshots. Assess:

**Layout:**
- [ ] No elements overflowing their containers
- [ ] Consistent spacing (not too tight, not too loose)
- [ ] Responsive? (try 390px mobile width if applicable)

**Typography:**
- [ ] Text is readable (contrast, size)
- [ ] No truncation where unexpected

**Colors:**
- [ ] Follows design system (blue for actions, green for success only — see CLAUDE.md)
- [ ] No amber/orange/purple/yellow in UI

**Interactions:**
- [ ] Feedback is immediate (loading state, toast, state change)
- [ ] Buttons look like buttons
- [ ] No "dead click" moments (user clicks, nothing visible happens)

**Overall impression:**
- [ ] Looks intentional, not hacked together
- [ ] A user seeing this for the first time would trust it

Skip this step if only functional accuracy matters (e.g., a backend bug fix).

Report the visual pass:
```
Visual quality: ✅ Looks great / ⚠️ Minor issues / ❌ Needs work
Issues: {list if any}
```

---

### Step 7: Update UAT Scorecard

If `features/uat/p{N}.md` exists, update the Test Execution Log:

```markdown
| UAT-2.1 | ✅ | Toast: "Verify your email to create a story — check your inbox or resend below." |
| UAT-2.2 | ✅ | Story created, redirected to /story/abc123 |
| UAT-3.1 | ❌ | Old message still appears: "Please verify your email to record positions" |
```

Replace the `⬜` entries for each scenario you tested.

---

### Step 8: Report

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
P{N} Verification Report
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Functional: {passed}/{total} scenarios passed
Visual quality: {✅ / ⚠️ / ❌}
UAT scorecard: updated

PASSED ✅
  UAT-2.1: Unverified user sees correct toast on /create
  UAT-2.2: Verified user creates story successfully
  UAT-5.2: /live redirects unverified users

FAILED ❌
  UAT-3.1: Wrong toast on position gate — still shows old message
    Expected: "Verify your email to set a position — check your inbox or resend below."
    Got: "Please verify your email to record positions"
    → This is a HIGH issue. Feature is NOT shippable as-is.

VISUAL ISSUES ⚠️
  Toast sits too close to the bottom nav on mobile (375px). Small padding fix.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
VERDICT: ❌ Not ready to ship
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Fix UAT-3.1 failure, then re-run `/verify p{N}` to confirm.
```

**Verdict rules:**
- `✅ Ready to ship` — All functional scenarios pass, visual quality ✅ or ⚠️ with only minor issues
- `⚠️ Ship with caveats` — All functional pass, visual has real issues worth fixing but not blockers
- `❌ Not ready` — Any functional scenario fails

## How This Skill Works for P273

**Spec:** `features/p273_bug-create-story-unverified-error.md`
**UAT file:** `features/uat/p273.md` (11 scenarios)

**What the skill does:**

1. Reads UAT-2.1 → UAT-5.2 scenarios
2. Opens `localhost:5001`
3. Checks current auth state
4. **UAT-2.1 (unverified user → /create):**
   - Asks you to switch to an unverified test account
   - Navigates to `/create`
   - Fills in "Remote work improves team communication"
   - Clicks "Create a Story"
   - Screenshot → checks for toast containing "Verify your email to create"
   - Also confirms "Save failed" is NOT present
   - Checks DB via console: no story created
5. **UAT-2.2 (verified user → /create):**
   - Asks you to switch to your normal verified account
   - Same flow → expects success toast + URL change to `/story/:id`
   - No verification toast visible
6. **UAT-3.1 (unverified → position button):**
   - Navigates to any story detail with points
   - Clicks a position button
   - Screenshot → checks toast text matches hook spec exactly
   - Confirms old message "Please verify your email to record positions" is GONE
7. **UAT-5.2 (/live protection):**
   - Navigates to `/live` as unverified user
   - Confirms redirect happens
8. **Visual pass:** Takes screenshot of the toast, judges: correct font, correct color (error = red), readable, not overlapping bottom nav on mobile

**Result:** A clear ✅/❌ verdict per scenario with screenshots + verbatim toast text captured.

## Escalation Protocol

If ❌ verdict:
1. **List failures clearly** — exact scenario, what was expected, what happened
2. **Suggest the fix** — "UAT-3.1 failed: looks like `story-detail-page.tsx` still uses the old one-off check. The hook migration may be incomplete."
3. **Tell user next step** — "Fix the issue, commit, then run `/verify` again."

If ⚠️ verdict (visual issues only):
1. List them as non-blocking
2. Ask: "Fix visual issues now or ship anyway? (fix/ship)"

## Edge Cases

| Situation | Behavior |
|-----------|----------|
| No UAT file exists | Derive scenarios from spec's "Acceptance Criteria" section |
| No acceptance criteria section | Derive from any "Given/When/Then" or "must/should" statements in spec |
| Scenario needs unauthenticated state | Ask user to open incognito tab, use that for that scenario |
| Scenario requires DB setup (create N records) | Tell user what to set up, wait for confirmation |
| Page doesn't exist yet | ❌ Fail immediately — page not found is a functional failure |
| Dev server on different port (worktree) | Auto-detect from vite.config.ts |
