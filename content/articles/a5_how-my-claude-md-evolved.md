# Every line in my CLAUDE.md is a mistake that cost me time

## The idea

Walk through the evolution of my CLAUDE.md — not the polished result, but the **decisions behind it**.

Each rule traces back to a specific failure:
- what happened
- how long it cost me
- what rule I added to prevent it next time

This is interesting because most people see CLAUDE.md advice as generic ("add context!") but don't see the **mechanics of why specific rules matter** and what failure mode they're each defending against.

## Angle

Not "here's how to write a good CLAUDE.md" — but "here's what my CLAUDE.md *is* — a log of mistakes."

The rules aren't opinions. They're scar tissue.

Readers who are building their own Claude configs will recognize their own pain points in the list. And they'll have a concrete starting point instead of a blank file.

## Potential structure

- Hook: my CLAUDE.md is X lines. Every line is a mistake I made.
- Pattern: mistake → time lost → rule added (pick 4-5 most relatable ones)
  - e.g., agent silently worked around a problem → Transparency Principle
  - e.g., agent made a "clever" improvement I didn't ask for → Scope creep rule
  - e.g., infra setup, wrong tool chosen, hours lost → Before Choosing Infrastructure Tools rule
  - e.g., two Claude sessions staging each other's files → Parallel Feature Work / Index Collision Risk
  - e.g., asked for opinion, got "it depends" → Decisive Action / Anti-Sycophancy
- Takeaway: your CLAUDE.md should grow from pain, not from theory. Start with one rule. Add the second after the next failure.
