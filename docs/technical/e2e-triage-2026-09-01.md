### How the 580 was measured — and how the first attempt undercounted

Every one of the 244 failing spec files was mapped to its P-number and that P-number's spec
frontmatter was read. **61 files** carry `status: rejected` (17 files / 216 failures),
`superseded_by:` (39 / 320), or are named by a *successor's* `predecessor:` field (5 / 44).

**The first pass of this sweep reported 536 and was wrong.** It checked only the failing spec's own
frontmatter — `status:` and `superseded_by:`. But a supersession can be recorded only on the
*successor* side: `p502_anon_position_optimistic_ui.md` carries `predecessor: p458`, while P458's own
spec still reads `status: all-done` with no marker at all. A check that reads only the predecessor's
frontmatter cannot see that, and silently classified 44 failures across 5 files as "live spec".
The gap was found by the p458 triage agent, not by the sweep, and the number above is the corrected
one. **Any future sweep must walk the chain from both ends.**

Six files are confirmed dead by independent reproduction plus a traced superseding commit:
p526, p523, p476, p456 (rejected/superseded) and p458, p152 (predecessor chain).

**Caveat that must travel with this number:** for the remaining files, the frontmatter is a strong
prior, not proof. A superseding spec may have kept most behaviour. Each still needs a per-file check.

## Genuine product defects (each verified in source by the orchestrator — two agent claims were corrected in the process)

1. **Nested interactive controls on the point card** — `src/app/components/social/point-card-with-links.tsx:272`
   sets `role="button" tabIndex={0}` on the card wrapper with **no** `aria-label`, while the CTA
   `<button aria-label={ctaCopy.ariaLabel}>` (line 109) is a DOM descendant. The wrapper's accessible
   name is computed from its subtree, so it inherits the inner button's label and both elements match
   the same locator. A real HTML/ARIA violation. p465's own test for exactly this
   (`e2e/a11y/p465-accessibility.spec.ts:288`) never fired, because that file navigates to the wrong route.

2. **"Add image" has nowhere to render in view mode** — `src/app/components/social/StoryCardDetail.tsx:343`
   gates the entire media block on `{(story.videoUrl || imageUrl) && …}`. A story with no image has no
   media block, so no add-image affordance can appear. The only such button lives behind `isEditMode`.
   Spec `features/done/27_mar_27/p591.md` UAT-7 and UAT-19 expect it in the plain view state.
   **This is a shipped-as-done AC that was never built.**

3. **Lightbox accessible name is silently overridden** — `src/app/components/shared/image-lightbox.tsx:42`
   sets `aria-label="Full-size image view"` on the Dialog content, but a sibling
   `DialogPrimitive.Title` holds the per-story alt text. Radix wires `aria-labelledby` to the Title,
   and `aria-labelledby` beats `aria-label`, so the intended name never applies.

4. **Feed tab bar has no keyboard navigation** — `src/app/pages/feed-page.tsx:350-379` renders
   `role="tablist"` with plain `<button role="tab" onClick>`. `grep -c "onKeyDown\|ArrowRight\|ArrowLeft"`
   over the whole file returns **0**. Spec `features/done/22_mar_26/p491_hashtag_feed.md:670` required
   "Arrow keys navigate between tabs (Left/Right)", and explicitly rejected a tabs library on the
   grounds that "the accessibility requirements … are simple enough to implement inline."
   **A second shipped-as-done AC that was never built.**

5. **The empty-creator-name guard on agreement creation has never worked** —
   `src/app/pages/create-agreement-page.tsx:308` computes
   `creatorHasNoName = creatorName !== undefined && !creatorName`, where `creatorName` comes from
   `user?.name` (line 113). But `src/app/data/api.ts` maps every profile as
   `name: dbProfile.name || 'Anonymous'` (lines 556 and 593), so `user.name` is never falsy and the
   guard's second clause is always false. A user with a blank name silently creates an agreement as
   "Anonymous" instead of being blocked.

   **The triage agent attributed this to a later commit (`40aaa82a`, p1149) as a side effect. That
   attribution is wrong, and the truth is worse.** `40aaa82a` does touch `api.ts` but adds no
   `|| 'Anonymous'` line (`git show … | grep -c "^+.*|| 'Anonymous'"` → 0). The fallback entered on
   **2025-12-01** (`9c9b6015`); the guard was written on **2026-03-02** (`3a658df0`, P466). Reading
   `api.ts` *as of the guard's own commit* finds the fallback already present, twice.
   **The guard was born dead — it has never fired once.** Its test (`agreements.spec.ts` TC-10) has
   been failing the whole time.

   **This is the third instance of the same class**, alongside P591 UAT-7/19 and P491's arrow keys:
   an acceptance criterion that shipped, was never satisfied, and had a test saying so in a suite
   nobody ran.

## The test project's schema has drifted from prod — four independent instances

This category is the one no single triage agent could see whole, because each met only its own
symptom. **In every case the test project is behind, and prod is correct.** The E2E suite runs
against test, so these failures are environment drift, not product defects — but the drift itself
is a real operational problem, and one instance is security-shaped.

### 1. P1114 column grants on `event_room_members` — test is stuck at the base migration

Measured by read-only REST with controls that discriminate (`42703` = no such column,
`42501` = column not granted, and a control column that cannot exist returns `42703`):

| column | TEST | PROD | intended (per `20260821170000`) |
|---|---|---|---|
| `comprehension_rating` | **42501 denied** | readable | readable |
| `readiness_value` | **readable** | 42501 denied | denied |
| `client_secret` | — | 42501 denied | denied |

TEST's live grant is exactly the base `20260819161000` list. Both later migrations
(`20260821120000`, `20260821170000`) use an explicit **REVOKE-then-GRANT** idiom, so the "column
grants are additive in Postgres, therefore nothing was revoked" explanation is ruled out — had
either applied, `readiness_value` would be gone and `comprehension_rating` present. Neither grant
block took effect on test.

**`readiness_value` is anon-readable on the test project when the chain intends it revoked** — the
migration's own comment says it "joins `client_secret`" in being excluded. **Prod is not affected.**

The knock-on explains all 20 p1114 failures as one swallowed error, not seven UI bugs:
`src/app/data/event-room-service.ts:183-186` selects `comprehension_rating` by name, catches the
`42501` and returns `[]` by design ("never an error state or an empty wall"), so
`EventRoomMeet.tsx:410-418` renders "Loading who is here…" forever.

**The p1114 integration test is not stale — it is correct, and it caught this.** It is one of the
few tests in the run doing exactly the job a test exists to do.

*Open question, not resolved:* why the GRANT statements specifically failed to apply while
`ALTER TABLE`, `POLICY` and `FUNCTION` statements in the same files did. That needs direct
`information_schema` introspection, which a read-only REST probe cannot do.

### 2. P967 — a migration edited in place, so the fix never redeployed

`supabase/migrations/20260627120000_p967_listener_calibration_rpc.sql` now reads
`NULL::TEXT AS story_title` (line 37). `git log` on that file shows **two** commits: `09825301`
created it, and `6fb85e10` ("RPC uses NULL story_title — stories.title was dropped in P701")
fixed it **by editing the same file**. Migration tooling tracks applied state by version/filename,
so the corrected body was never pushed; the deployed function on test still references `s.title`
and returns `42703` once P701's drop finally landed on test (2026-08-24).

This is the P1042 anti-pattern the repo has already been bitten by: **fixing an applied migration
in place instead of adding a forward one.**

### 3. An orphaned `seal_and_send_letter` overload — known, documented, never dropped

Found independently by two groups (p651 and the migration-named integration specs), and it is the
most-reaching schema defect in the run: **11 failures across 7 spec files**.

`seal_and_send_letter` has four `CREATE OR REPLACE FUNCTION` definitions across the chain and
`DROP FUNCTION` for it appears **nowhere**. P952 added a 4th parameter with a `DEFAULT`, which in
Postgres creates a *new overload* rather than replacing the 3-arg one. PostgREST then cannot resolve
a 3-arg call and returns `PGRST203` ("could not choose the best candidate function").

**The repo already knows.** `20260813080000_p1063_...sql` says so in its own header:

> creating a function under a NEW SIGNATURE (P952 added the p_responses_mode argument to
> seal_and_send_letter) creates a genuinely new function that gets the default PUBLIC grant

That migration then revokes and re-grants **both** overloads by explicit signature (lines 84-85,
92-93, 100-101). Since `REVOKE EXECUTE ON FUNCTION` errors on a function that does not exist, that
migration having applied is itself proof both overloads are live — no RPC call needed to
demonstrate it. P1063 fixed the *privilege* consequence of the duplicate and left the duplicate.

**Production is not affected:** `src/app/data/letters-service.ts:103-109` always passes 4 arguments,
and P1063 locked both overloads to `authenticated`. What is broken is the backward-compatibility
path the `DEFAULT` was presumably added to provide. A forward migration dropping
`seal_and_send_letter(uuid, jsonb, jsonb)` fixes all 7 files with **no test edits at all** — the only
finding in this triage with that property.

### 4. Unexplained: `service_role` refused by RLS on `clarity_sessions`

A triage agent reproduced, live, `supabaseAdmin.from('clarity_sessions').insert(...)` failing with
`new row violates row-level security policy` — using a key I independently confirmed decodes to
`role=service_role` on the right project ref. Service-role is supposed to bypass RLS, and the same
key demonstrably does so elsewhere.

`ALTER TABLE ... FORCE ROW LEVEL SECURITY` — the usual explanation, since it applies RLS even to the
owner — **appears nowhere in any migration** (`grep -rn` over `supabase/migrations/*.sql`: no hits).
So the obvious cause is ruled out and the mechanism is genuinely unknown.

This is recorded as **unresolved, not diagnosed**. It needs `rolbypassrls` checked on `service_role`
in the test project, which REST cannot introspect. It is worth closing rather than filing away: if
service-role writes can be refused, that reaches admin and E2E tooling far beyond this one test.

### CORRECTED 2026-09-01, same day: the leak is real, its blamed effect was not

**What this section originally claimed:** that 110 identically-named leaked rows caused
`point-position-persistence.spec.ts` to fail — a strict-mode violation (2+ matches) in one test and
0 matches in another, "irreconcilable under any rendering theory."

**That causal claim is false, and the disproof was making the fix.** The fixture statement was made
unique per run (`${Date.now()}-${random}`) and the file re-run. With a point whose name is
guaranteed unique, **the strict-mode violation persists**:

```
strict mode violation: locator('.border-l-4')
  .filter({ hasText: 'E2E Test Point: ... 1788239834378-vzwp8t' })
  .getByText(/Agrees|Disagrees|Unsure/) resolved to 2 elements:
    1) <span ...>Disagrees</span>
    2) <span>Unsure</span>  aka getByTestId('unsure-group')
```

Both elements are inside the **same** card. The locator matches the position badge *and* a separate
`unsure-group` element. It is an over-broad locator, not data contamination. Test counts before and
after the uniqueness change are identical: 3 failed / 2 passed.

**What survives, and is now better evidenced than before.** The leak itself is real and *ongoing*,
measured by a controlled before/after rather than a single snapshot:

| | before the run | after one 5-test run |
|---|---:|---:|
| rows with the old hardcoded statement | 110 | 110 |
| rows with the new unique statement | 0 | **5** |

Five tests ran; five rows survived. `afterEach` **does** issue
`supabaseAdmin.from('points').delete().eq('id', testPointId)` — an earlier version of this section
said it did not, which was also wrong — and the rows remain anyway. The delete's result is never
checked, so whatever prevents it is silent.

**The mechanism is unresolved.** Three candidates were raised and two were falsified: an FK blocking
the delete (the point FKs are `ON DELETE CASCADE`), and cleanup never being written (it is). The
surviving hypothesis — a timed-out test losing its teardown budget — is **untested**. Do not quote
it as the cause.

**The lesson that generalises** is not about this file. A count is evidence that rows exist; it is
not evidence of what they break. The correlation here was strong, the sample was one file, and the
conclusion was wrong. The only thing that settled it was changing one variable and re-running.

### Why this matters beyond one file

A suite running against a database with 2,107 leftover fixture points is not measuring what it
believes it is measuring. Any assertion that locates an element **by fixture text** is exposed:
`getByText`, `filter({ hasText })`, and every `.first()` written to paper over an earlier collision.
It was tempting to read this as a contributor to the run's strict-mode violations generally. **That
inference is now explicitly withdrawn** — the one case tested in detail turned out to be an
over-broad locator instead. Treat the pollution as an untested risk to text-based assertions, not as
an explanation for any specific failure.

**Stated honestly:** the causal link is *disproven* in the one file where it was tested, and untested
everywhere else. **No failure in this run is currently attributed to test-data pollution.** The
pollution is real, growing, and worth fixing on its own terms — not as a failure explanation.

**This is also a warning about the run itself.** Before the next overnight run is treated as a
clean baseline, someone has to decide whether the test project gets truncated first — and that is a
destructive operation on a shared database, so it is a founder call, not a cleanup task.

## Runner defects fixed in this branch

Three defects were found by an adversarial review *after* the run started and deliberately left
unfixed (editing a running bash script can corrupt the process). All three are fixed here, and each
fix was exercised on its failure path, not assumed.

1. **`verdict: "complete"` could be a lie.** `CLASSIFY_RC` and `BATCHES_FAILED_TO_START` were logged
   and never consulted; the verdict keyed only off `$CUTOFF`. Now keys off all three.
   Exercised: all five input combinations run: the known-good control still returns `complete`;
   both previously-silent paths now return `partial`.

2. **Playwright reused a foreign dev server.** `reuseExistingServer: !process.env.CI` and the runner
   never set `CI`, so Playwright reused whatever was on port 5001 and never applied its own `env:`
   block — a Phase A local unlock would never reach the browser while the report still claimed
   "Ran on a local unthrottled stack". Setting `CI=1` would have fixed the reuse but also silently
   changed workers (3→2) and retries (1→2), i.e. changed what the run measures. Instead the runner
   now **starts and owns its own dev server** with the env the run resolved, and **refuses to start**
   if the port is already served by a foreign process.
   Exercised: probe returns true on an occupied port, false on a free one; the abort branch exits 3.

3. **A dev server dying mid-night silently invalidated every later batch.** `ensure_dev_server` now
   health-checks between batches and restarts, with the restart count surfaced in the morning report.
