# Implementation Patterns

Patterns discovered through building the sequential spec-driven delivery pipeline. Reference for agents and developers.

---

## 1. Spec-as-Reference

**Problem:** Loading a 700+ line spec into agent context wastes tokens and risks overflow.

**Pattern:** Agents fetch only the sections they need, by line offset/limit.

- Task manifests include spec section references with approximate line ranges: `"UX Design > Story Picker (lines ~356-395)"`
- Subagents use `Read` with `offset` + `limit` parameters instead of reading the full file
- Each skill reads only its input section: `/decompose` reads `### Implementation Approach`, `/dev` (orchestrator) reads `## Implementation Tasks`

**Rule:** Never pass a full spec to a subagent. Always slice to relevant sections.

---

## 2. Atomic Task Boundary

**Problem:** Tasks that span multiple files and concerns are hard to verify and cause merge conflicts between concurrent subagents.

**Pattern:** Each task = 1–3 files, one concern, independently verifiable.

Natural boundaries:
- DB migration → one task (files: `supabase/migrations/*.sql`)
- Service function or hook → one task (files: `src/lib/...` or `src/app/hooks/...`)
- UI component → one task (files: `src/components/...` or `src/app/.../page.tsx`)
- Wiring / integration → one task (connects existing pieces, touches entry points)
- Test stubs → one task (can be per-feature or grouped per concern)

**Anti-pattern:** `Task 1: DB schema + service layer + UI component`. This is three tasks.

**Verify step:** Every task must have a one-line verification that can be confirmed without running the full feature (type check, migration dry-run, unit test, visual check).

---

## 3. Complexity Tiers

Three tiers, different execution strategies:

| Tier | Threshold | Strategy |
|------|-----------|----------|
| Simple | < 5 files AND < 3 concerns AND < 6 steps | `/dev` directly (reads full spec, single pass) |
| Medium | 3–5 files, 3–5 steps | `/dev` or ralph-loop (both work; ralph better if 10+ iterations expected) |
| Large | 5+ files OR 3+ concerns OR 6+ steps | `/decompose` → task manifest → `/dev` orchestrator |

**Routing logic:**
- `/generate-ralph-loop` checks complexity first and recommends tier
- `/decompose` enforces the large-feature threshold (stops if below it)
- `/dev` auto-detects which mode to use based on `## Implementation Tasks` presence

---

## 4. Task Manifest Format

The `## Implementation Tasks` section in a spec file is the orchestration interface between `/decompose` and `/dev`.

**Structure:**
```markdown
## Implementation Tasks

> Generated by /decompose. Each task is scoped to 1–3 files and independently verifiable.
> Run /dev to execute — it will dispatch one subagent per task.

### Task N: [title]
- **Files:** `path/to/file.ts` (create), `path/to/other.ts` (modify)
- **Spec refs:** "Section > Subsection (lines ~N-M)"
- **Depends on:** Task N, or "None"
- **Verify:** one-line verification
- [ ] Complete

**Total tasks:** N | **Can parallelize:** Task X, Y | **Must be sequential:** A → B → C
```

**Conventions:**
- `[ ] Complete` → unchecked (pending)
- `[x] Complete` → checked (done, committed)
- Tasks without dependencies can run as concurrent subagents
- /dev commits after each task (partial progress is preserved)

---

## 5. Compaction Avoidance

**Problem:** Long agent sessions accumulate context, leading to compaction. Compacted sessions forget earlier work and produce inconsistent output.

**Pattern:** Architect tasks to avoid compaction — don't recover from it.

- **Subagents get fresh context:** Each task subagent starts with only its task description + relevant spec lines. No accumulated history.
- **Small tasks = small context:** Atomic task boundaries keep each subagent's working context small (1–3 files + spec slice).
- **Commit early:** /dev commits after each task. If a session compacts mid-feature, the already-committed tasks are safe.
- **Checkpoint with checkboxes:** `[x] Complete` marks let /dev resume from the last completed task without re-reading all prior work.

**Anti-pattern:** One large subagent that implements 8 tasks in sequence. By task 6, context is degraded.

---

## Delivery Stage Values (Large Feature Path)

```
prd-review → prd-approved → ux-review → ux-approved → arch-review → arch-approved → decompose-review → decompose-approved → tests-generated → implementation → done
```

`arch-approved` and `decompose-approved` are set when the user approves the respective layer. `/decompose` moves `arch-approved → decompose-review` after generating the task manifest.
