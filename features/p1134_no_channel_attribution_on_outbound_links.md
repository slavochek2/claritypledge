# P1134: No channel attribution on outbound links

## Problem

**Situation:** In a 30-day traffic review, 99% of visitors (1,949 of 1,960) showed no referrer at
all in Mixpanel ($direct) — only ~11 were attributable to Facebook, Google, or the blog subdomain.
Top-traffic pages include `/cm` (an embedded Chiang Mai events calendar, 394 pageviews — the
single highest-traffic page on the site) and one pledger's public profile page (40 pageviews in 30
days, despite that pledger never logging in again after her original signup).

**Complication:** None of the site's outbound-facing links — event promotion posts, WhatsApp/
Telegram shares, the `/cm` calendar's own "Add this calendar to yours" link, individual pledgers
sharing their own profile — carry any channel-identifying parameter. Every one of them collapses
into the same undifferentiated `$direct` bucket regardless of source. There is currently no way to
tell which specific promotion, event, or person is driving any given batch of visitors — including
the open question of why the Chiang Mai calendar page and that one pledger's profile
disproportionately outperform every other page.

**Question:** How do we tag outbound links so Mixpanel can attribute visits to a specific channel,
campaign, or sharer — without building a new attribution system from scratch?

## Appetite

**Blast radius:** low — this is additive query-string tagging on links plus (possibly) exposing
one already-captured property as a clean breakdown dimension. No existing page behavior, route, or
component logic changes based on the presence/absence of these params.

**Reversibility:** fully reversible — removing UTM params from a shared link, or stopping the
practice, has zero downstream effect on site behavior.

**Decision density:** low — this is largely mechanical once the open verification question below
is answered. One judgment call: which existing outbound touchpoints get retrofitted with the
convention now vs. left for "apply it going forward."

## Solution

Adopt the standard `utm_source` / `utm_medium` / `utm_campaign` query-param convention for every
outbound link this project controls, and verify Mixpanel surfaces those params as clean,
breakdown-usable properties.

**Open verification — do not build custom capture code before checking this.** Mixpanel's
pageview event already includes a `current_url_search` string property (confirmed present on
`$mp_web_page_view` via `List-Properties`), meaning the raw query string — UTM params included —
is already captured passively on every pageview today, even though nothing currently puts UTM
params on any link. What's unconfirmed: whether Mixpanel's autocapture (enabled in `index.html`,
`autocapture: { pageview: true, ... }`) also promotes `utm_source`/`utm_medium`/`utm_campaign` into
their own first-class event/user properties (Mixpanel's documented default behavior), or whether
`current_url_search` is the only place they'd land. **Verify before writing any code:** append
`?utm_source=test&utm_medium=test` to a local/staging pageview, check Mixpanel live view for a
`utm_source` property on the resulting event. If it's not automatic, add explicit parsing in
`src/lib/mixpanel.ts`'s pageview path (or wherever `$mp_web_page_view` autocapture is configured)
to extract and forward the three params.

Once verified, apply the convention going forward to the outbound touchpoints already identified
this session:
- The `/cm` page's own "Add this calendar to yours" subscribe link
- Event-promotion content generated by the `slava:events:promote-*` skills (Facebook, WhatsApp,
  email, Luma, Eventbrite, etc.) — each gets a distinct `utm_medium`/`utm_campaign` so channels are
  distinguishable from each other, not just from $direct
- The existing `?referrer=<profile_id>` person-to-person share mechanism (`witness-card.tsx` and
  similar) — leave as-is; it already answers "which person," which is a different question from
  "which channel." Do not conflate the two mechanisms.

## Risks / Non-Goals

### Risks
- **[MITIGATE] Retrofitting is manual and easy to forget on the next new share surface.** A single
  documented convention (see Done-When) with one short helper (e.g. a `withUtm(url, {source,
  medium, campaign})` function) in a shared location makes the correct path the easy path, rather
  than every promo skill hand-rolling query strings.
- **[ACCEPT] This does not retroactively attribute the 99% of already-collected $direct traffic.**
  That data is genuinely unattributable — the fix only prevents new traffic from landing in the
  same undifferentiated bucket.
- **[ACCEPT] Some traffic (in-person QR codes, printed materials, verbal mentions) may still be
  hard to tag or may not survive the medium** (e.g. some chat apps strip query strings on link
  preview). Full coverage isn't achievable; this is about closing the largest gap, not all of it.

### Non-Goals
- Do NOT build a UTM builder UI, campaign dashboard, or attribution reporting tool — this spec is
  about tagging links and confirming capture, not analysis tooling.
- Do NOT touch or duplicate the existing `?referrer=<profile_id>` person-to-person share mechanism
  — it solves a different problem (who) and stays as-is.
- Do NOT retrofit every historical outbound link across every past promotion — apply going forward
  plus the specific `/cm` touchpoint named above; a full historical audit is out of scope.
- Do NOT change what data Mixpanel autocapture collects beyond confirming/exposing UTM params —
  no new custom event types.

### Alternatives Considered
- **Build a custom short-link/redirect service that logs clicks server-side.** Rejected — much
  higher blast radius (new infra, a redirect hop on every shared link) for a problem the existing
  Mixpanel autocapture likely already solves once UTM params are present in the URL.
