# P882: Sentry noise — unhandled "Error: Rejected" from PWA service-worker registration (JAVASCRIPT-REACT-19)

## Summary

Sentry issue JAVASCRIPT-REACT-19 ("Error: Rejected", culprit `/manifesto`, 11 events since Apr 23, 0 users impacted) is an unhandled promise rejection from the vite-plugin-pwa-generated `registerSW.js` — `navigator.serviceWorker.register('/sw.js')` rejects in automated/bot browsers and the existing `ignoreErrors` patterns don't catch it.

## Root Cause

Two layers:

1. **Source of the rejection:** `/registerSW.js` (generated by `vite-plugin-pwa`, configured in `vite.config.ts:123`) calls `navigator.serviceWorker.register('/sw.js')` without a `.catch()`. In clients where registration rejects, the browser fires `onunhandledrejection`, which Sentry captures (`mechanism: auto.browser.global_handlers.onunhandledrejection`).
2. **Why the existing filter misses it:** `src/main.tsx:45` already has `ignoreErrors: [/Rejected.*serviceWorker/i, /serviceWorker.*register/i]` — but `ignoreErrors` matches the error *message*, which is literally just `"Rejected"`. The serviceWorker context only appears in the **stack frames**. The comment at `main.tsx:34` even predicted this: "consider using beforeSend to check stack traces."

The stack frame `wrsParams.serviceWorkers.navigator.serviceWorker.register` is injected harness code — events are almost certainly crawlers/bots (consistent with 0 users impacted and `/manifesto` being a top crawl target).

## Reproduction Steps

1. Visit https://claritypledge.com/manifesto in a browser environment where `navigator.serviceWorker.register` rejects (e.g., stubbed SW in an automation harness, or some private-browsing modes)
2. `registerSW.js` runs on `load`, registration promise rejects
3. Observe: new event on Sentry issue JAVASCRIPT-REACT-19 ("Error: Rejected")

**Reproduction rate:** intermittent (only in clients where SW registration rejects — ~11 events / 40 days in prod)

## Expected Behavior

SW registration failure is a harmless progressive-enhancement no-op; no Sentry event is recorded.

## Actual Behavior

Each rejection creates a Sentry error event, keeping JAVASCRIPT-REACT-19 perpetually "unresolved" and polluting the weekly review.

## Affected Files

- `src/main.tsx` — lines 35–47 (`ignoreErrors` array; message-based patterns can't match this event) — add a stack-frame-based filter
- `vite.config.ts:123` — VitePWA config that generates `registerSW.js` (no change expected; noted for context)

## Severity

**Low** — pure observability noise; 0 users impacted, no functional effect.

## Fix Approach

Add a `beforeSend` hook in the `Sentry.init` options in `src/main.tsx` that drops events whose stack frames (exception or threads) include `/registerSW.js` (and/or whose mechanism is `onunhandledrejection` with message exactly `Rejected` originating from `serviceWorker.register`). Keep the existing `ignoreErrors` patterns. After deploy, resolve JAVASCRIPT-REACT-19 in Sentry.

- [ ] [post-deploy] After deploy: JAVASCRIPT-REACT-19 resolved in Sentry and does not regress for 7 days

## Resolution

**Root cause:** `ignoreErrors` is message-based; the event message is literally `"Rejected"` — the serviceWorker context exists only in stack frames, so the existing patterns never matched.

**Fix:** New `src/lib/sentry-filters.ts` exporting `dropServiceWorkerRegistrationNoise`, wired as `beforeSend` in `Sentry.init` (`src/main.tsx`). Drops events where any exception stack frame's `filename`/`abs_path`/`function` matches `/registerSW.js` or `serviceWorker.register`. Existing `ignoreErrors` patterns kept per spec.

**Regression test:** `src/tests/p882-sentry-sw-filter.test.ts` — drop via filename, abs_path-only, function-only, multi-value exception array; pass-through for real app errors, serviceWorker-adjacent function names, and no-exception events.
