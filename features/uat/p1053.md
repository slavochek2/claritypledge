# UAT: P1053 — Server-Side Join Authorization

Spec: [../p1053_server_side_join_authorization.md](../done/2026-06-10/p1053_server_side_join_authorization.md)

Automated coverage: `e2e/integration/p1053-claim-joiner-seat.spec.ts`. These scenarios cover
what cannot be automated in CI: prod deploy verification, grants re-read on prod after deploy
(the P877/P886 failure mode — a REVOKE that silently no-ops), and hand-confirmation of the
anonymous practice-room flows in a real browser, where the automated suite only proves the
database-layer contract.

**Read this before running any scenario below:** as of spec authoring (2026-08-12), neither
`claim_joiner_seat` nor the REVOKE exist yet. UAT-1 through UAT-6 assume the migration has
already been applied to the environment under test (test first, per the Verified-on-test-then-
prod requirement in Done-When). Do not run UAT-2 through UAT-6 against an environment where the
migration hasn't landed — they will all fail, and that failure carries no diagnostic value
beyond "not deployed yet."

## UAT-1: Migration applied on test — schema + grants exist

**Given:** `claim_joiner_seat` migration merged and `./scripts/migrate.sh` run against test.
**When:** Run the two schema-level checks below against the **test** DB.
**Then:**
```sql
-- (a) the RPC exists with the right signature
SELECT proname, pg_get_function_arguments(oid)
FROM pg_proc WHERE proname = 'claim_joiner_seat';
-- Expect: one row, arguments containing p_code and p_joiner_name.

-- (b) the REVOKE landed
SELECT grantee, privilege_type, column_name
FROM information_schema.column_privileges
WHERE table_name = 'clarity_sessions'
  AND column_name IN ('joiner_name', 'joiner_profile_id')
  AND grantee IN ('anon', 'authenticated');
-- Expect: ZERO ROWS. Any row here means the REVOKE did not land.
```
**Verify:** Paste both query outputs. `mcp__supabase__execute_sql` is fine here — it targets
test only (`.claude/rules/db-access.md`).

## UAT-2: Seat seizure — closed, confirmed against test via direct REST call

**Given:** Two test users, A (seated joiner) and B (attacker), a session where A already holds
the joiner seat.
**When:** As B (authenticated), `curl -X PATCH` the `clarity_sessions` REST endpoint against
**test**, `Authorization: Bearer <B's JWT>`, body `{"joiner_name":"A's name","joiner_profile_id":"<B's id>"}`, `?id=eq.<session id>`.
**Then:** Either a 403/42501, or a 204 with zero rows changed (PostgREST reports RLS/grant
denials both ways — do not treat "no error" as success).
**Verify:** Paste the curl response (status + body), then a service-role `GET` of the same row
showing `joiner_profile_id` still equals A's id. This is the same assertion the automated
"authenticated attacker cannot displace a joiner" canary makes — this scenario is the manual
proof that the REST layer (not just the JS client wrapper) enforces it.

## UAT-3: The six anonymous practice-room flows — by hand, in a real browser

**Given:** The migration deployed to test, `npm run dev` running against test.
**When:** In a real browser (Claude in Chrome or manual):
1. Create a session as a signed-in verified host.
2. Open the room link in an incognito/second browser context as an anonymous guest, join with
   a display name.
3. As the guest, submit a story/rating step that writes `state`.
4. Advance the live session so `live_state` + `mode` update (e.g. reach the rating phase).
5. If reachable in this build, trigger a `demo_status` transition.
6. Confirm the guest's presence syncs to the host's screen (proves `patch_live_state` still
   fires) — no `page.reload()`, just wait for the realtime/drift-poll update.
**Then:** Every step above completes with no console errors, no "Session not found or already
full" regression, and the guest's name/state is visible to the host without a reload.
**Verify:** Screenshots at each step (Visual QA checklist, `.claude/rules/visual-qa.md`,
desktop + 375px for the join screen at minimum). If any step fails, capture the console/network
error — the automated suite's six controls narrow down which specific write path broke.

## UAT-4: Rejoin-after-leave — by hand, the exact flow P1047 part 4 broke

**Given:** A session with a signed-in joiner already seated.
**When:** That joiner clicks "End Session" (or leaves), then a SECOND signed-in user opens the
same room link and joins.
**Then:** The second user joins successfully — no "Session not found or already full" after the
mic permission prompt (the exact user-visible symptom P1047 part 4 caused).
**Verify:** Screenshot of the second user's successful join. This is the highest-risk manual
check in this UAT — it is the regression the fix must not reintroduce.

## UAT-5: Departed participant still sees their own transcript

**Given:** A completed two-party session with a stored transcript (`session_transcripts` has a
row for it), where the joiner has since left.
**When:** The departed joiner logs in and navigates to their session history / the session's
detail view.
**Then:** The session appears in their history, and its transcript is viewable/retrievable —
not silently missing.
**Verify:** Screenshot of the transcript view. Also run the paired SQL check:
```sql
SELECT id, joiner_profile_id FROM clarity_sessions WHERE id = '<session id>';
SELECT id FROM session_transcripts WHERE session_id = '<session id>';
```
Paste both — `joiner_profile_id` must still equal the departed joiner's id.

## UAT-6: Deploy to prod, then re-read grants ON PROD

Done-When: "a REVOKE that silently no-ops is the P877/P886 failure".

**Given:** UAT-1 through UAT-5 all pass on test. Explicit founder approval to deploy to prod.
**When:** Deploy the migration to prod, then immediately re-run the grants check from UAT-1
against **prod** — using `psql "$SUPABASE_DB_URL"` from `.env.prod` (prod has no SQL-exec MCP;
`mcp__supabase__execute_sql` is test-only, `.claude/rules/db-access.md`):
```bash
psql "$SUPABASE_DB_URL" -c "
SELECT grantee, privilege_type, column_name
FROM information_schema.column_privileges
WHERE table_name = 'clarity_sessions'
  AND column_name IN ('joiner_name', 'joiner_profile_id')
  AND grantee IN ('anon', 'authenticated');"
```
**Then:** Zero rows. Additionally, run the functional proof against the live prod REST API
(not just the catalog query — P886 was caused by trusting a catalog-only check):
```bash
# Attempt a direct PATCH with the prod anon key against a disposable/known test row.
curl -s -X PATCH "https://besjtuodziykmjidubzw.supabase.co/rest/v1/clarity_sessions?id=eq.<row id>" \
  -H "apikey: $PROD_ANON_KEY" -H "Authorization: Bearer $PROD_ANON_KEY" \
  -H "Content-Type: application/json" -H "Prefer: return=representation" \
  -d '{"joiner_name":"prod-grant-check-should-fail"}'
```
Expect a 403 or an empty `[]` body (zero rows affected). Then re-`GET` the same row with the
service-role key and confirm `joiner_name` is unchanged.
**Verify:** Paste the `psql` output (zero rows), the curl response, and the service-role
readback. This is the single verification the spec calls out by name as the failure mode to
catch — do not skip it or infer it from the test-DB result.
