# UAT: P525 — Live State Deadlock Prevention

## UAT-1: Celebration "Continue" race — both users advance
**Given:** Two users are in a /live session, round just completed with score 10 (celebration screen visible to both)
**When:** Both users click "Continue" at approximately the same time
**Then:** Both acknowledgments persist — neither overwrites the other
**Then:** Session advances to next round (round counter increments, ratingPhase returns to idle)
**Then:** Neither user is stuck on the celebration screen
**Verify:** Two browsers side by side → both click Continue → both see idle state / next round. Check DB: `live_state` has `celebrationAcknowledgedByCreator: true` AND `celebrationAcknowledgedByJoiner: true` (briefly, before reset).

## UAT-2: Celebration "Continue" — sequential clicks still work
**Given:** Two users on celebration screen
**When:** Creator clicks "Continue" first, then joiner clicks "Continue" 5-10 seconds later
**Then:** After creator clicks, creator's button is disabled (waiting for partner). After joiner clicks, both advance.
**Verify:** Sequential clicks → same outcome as simultaneous. No regression from pre-P525 behavior.

## UAT-3: clickedContinue reverts on write failure
**Given:** User is on celebration screen and clicks "Continue"
**When:** The DB write fails (simulate: disable network briefly before clicking, or throttle network in DevTools)
**Then:** The "Continue" button re-enables after the failure
**Then:** User can retry clicking "Continue"
**Then:** Error appears in browser console (Sentry + console.error)
**Verify:** DevTools → Network → Offline → click Continue → button re-enables after ~5s timeout. Go back online → click again → succeeds.

## UAT-4: handleSkip clears selectedStoryData
**Given:** A round is in progress with a story selected (story card visible)
**When:** User clicks "Skip" (or "Good enough")
**Then:** Story data is fully cleared — no stale story card on the next round's idle screen
**Verify:** Select story → start round → skip → verify no story card remnant in idle state. Check DB: `live_state.selectedStoryData` is null/undefined after skip.

## UAT-5: updateInFlightRef timeout — no indefinite sync block
**Given:** User is in a /live session with normal connectivity
**When:** A state update takes longer than 5 seconds (simulate: DevTools → Network → throttle to slow 3G, then trigger a state update)
**Then:** After 5 seconds, the update times out
**Then:** Optimistic UI reverts (state shown matches server state)
**Then:** Polling resumes (session state syncs on next poll cycle)
**Verify:** Throttle network → trigger update → wait 5s → verify UI doesn't stay in an inconsistent state. Unthrottle → verify sync recovers.

## UAT-6: Sentry context set on session entry
**Given:** User joins a /live session
**When:** Session loads and partner connects
**Then:** Sentry context includes: session code, participant names, role (creator/joiner)
**Verify:** Trigger a test error (e.g., `Sentry.captureMessage('test')` in console) → check Sentry dashboard → confirm `live_session` context is attached with correct session code and role.

## UAT-7: Sentry breadcrumbs on phase transitions
**Given:** User is in a /live session
**When:** Phase transitions occur (idle → rating → explain-back → celebration → idle)
**Then:** Each transition creates a Sentry breadcrumb
**Verify:** Complete a full round → trigger a test error → check Sentry dashboard → breadcrumbs show the phase transition timeline.

## UAT-8: Sentry captures updateLiveState failures with sanitized data
**Given:** A state update fails in /live
**When:** Error is captured by Sentry
**Then:** Sentry event includes the error with `live_state` snapshot in `extra`
**Then:** Snapshot contains structural fields only (ratingPhase, currentRound, checkerSubmitted, etc.)
**Then:** Snapshot does NOT contain user names, story titles, or story content
**Verify:** Force a failure → check Sentry event → confirm no PII in the `extra` data. Look for: no `checkerName`, no `currentSpeaker`, no `selectedStoryData.title`.

## UAT-9: Mixpanel live_phase_transition fires on every phase change
**Given:** User is in a /live session
**When:** Phase changes (e.g., idle → rating)
**Then:** Mixpanel receives a `live_phase_transition` event with properties: `session_code`, `from_phase`, `to_phase`, `round`
**Verify:** Complete a round → check Mixpanel Live View → confirm `live_phase_transition` events appear for each transition.

## UAT-10: Mixpanel live_state_update_failed fires on write failure
**Given:** A state update fails in /live
**When:** Error occurs
**Then:** Mixpanel receives a `live_state_update_failed` event with properties: `session_code`, `error_message`, `attempted_keys`, `phase_at_failure`
**Verify:** Force a failure (offline toggle) → check Mixpanel Live View → confirm event appears with correct properties.

## UAT-11: Backward compatibility — old-code user + new-code user
**Given:** One browser has cached old bundle (celebrationAcknowledgedBy array), other has new bundle (boolean keys)
**When:** Both users complete a round and click Continue
**Then:** Session still advances — dual-read logic handles the mixed format
**Verify:** This is difficult to test manually. Primary verification: code review confirms dual-read logic OR-checks both old array and new booleans. Secondary: deploy new code, have one user hard-refresh (new code) while other uses cached version.

## UAT-12: No regression — happy path session flow
**Given:** Two users in a /live session
**When:** They complete a full round (select story → rate → explain back → celebrate → continue)
**Then:** All phases transition correctly, celebration completes, next round starts
**Then:** No new errors in browser console, no stuck states
**Verify:** Full round in two browsers → verify smooth flow. This is the regression check for all P525 changes.
