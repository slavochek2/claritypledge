# P651 UAT: Letter 1-to-1 Recipient Onboarding Redesign

Manual validation scenarios for P651. Run against local dev or staging.

## UAT-1: New user 1-to-1 letter flow (full path)

**Given** a sender has composed and sealed a 1-to-1 letter to a new email address (no existing account), with `receiver_name` "Jan Kovac"
**When** the recipient clicks the email link and lands on the cover page
**Then** the cover shows:
- "For Jan" (first name from receiver_name, not full email)
- "From [Sender's display name]" (not a UUID)
- A single "Open the Letter" button
- "By opening, you accept ToS" text

**When** the recipient clicks "Open the Letter"
**Then**:
- A loading state appears briefly (button disabled / spinner)
- The recipient is automatically authenticated (account + profile created via `create-and-open-letter` edge function)
- Reading flow begins immediately (story content visible)
- No "Sign in to continue" wall appears at any point
- Rating buttons are accessible without additional auth steps
- On completion, no "Save your results?" gate appears

## UAT-2: Existing user 1-to-1 letter flow

**Given** a sender has composed and sealed a 1-to-1 letter to an email address that already has a ClarityPledge account
**When** the recipient clicks the email link and lands on the cover page
**Then** the same cover as UAT-1 appears

**When** the recipient clicks "Open the Letter"
**Then**:
- The existing account is linked to the delivery
- The recipient is authenticated via `verifyOtp` (instant, no email round-trip)
- Reading flow begins with full identity (ratings linked to their profile)

## UAT-3: verifyOtp failure fallback

**Given** a 1-to-1 recipient clicks "Open the Letter" but `verifyOtp` fails (e.g., token expired)
**When** the fallback fires
**Then**:
- `signInWithOtp` is called with the recipient's email
- The recipient sees a "Check your email" message or is redirected to complete auth via magic link
- After magic link auth, the recipient returns to the letter reading page authenticated

## UAT-4: Name displayed on cover and in email

**Given** a sender entered "Slava Ladischenski" as the recipient name during composition
**When** the recipient receives the invitation email
**Then**:
- Email greeting says "Hi Slava," (first name)
- Email copy says "you'll be able to create an account when you open the letter" (not "automatically")

**When** the recipient lands on the cover page
**Then**:
- Cover shows "For Slava" (first name from receiver_name)
- Cover shows "From [Sender's name]" (resolved from profiles, not UUID)

## UAT-5: 1-to-many flow unchanged

**Given** a sender creates a 1-to-many letter (mode = "Anyone with a link")
**When** any user visits the letter URL (no token needed)
**Then**:
- Cover shows "Open the Letter" (no auth)
- Reading starts anonymously (no account creation)
- "Sign in to continue" appears at the rating phase (expected for anonymous)
- Completion shows "Save your results?" gate (expected for anonymous)
- This flow is identical to pre-P651 behavior

## UAT-6: Composition — name input

**Given** a sender is on the letter composition wizard
**When** they select "Specific people" mode
**Then**:
- A name input field appears alongside the email input
- Name is required — the Add/Continue button is disabled without it
- "Anyone with a link" mode does NOT show a name input

**When** the sender fills both name ("Jan Kovac") and email, adds the recipient, and proceeds to seal
**Then**:
- The seal/preview summary shows "Jan Kovac (jan@example.com)" format
- After sealing, `letter_deliveries.receiver_name` = "Jan Kovac" in the database

## UAT-7: Bug fix verification — status regression

**Given** a delivery with status "completed"
**When** `update_delivery_status_by_token` is called with p_status = "sent"
**Then** the status remains "completed" (backward transition rejected)

## UAT-8: Bug fix verification — sealed-bid scoping

**Given** a sender sent two 1-to-1 letters with overlapping stories to different recipients
**And** Recipient A has rated Story X but Recipient B has NOT
**When** Recipient B calls `reveal_prediction_by_token` for Story X
**Then** the prediction is NOT revealed (sealed-bid intact per delivery)

**When** Recipient A calls `reveal_prediction_by_token` for Story X
**Then** the prediction IS revealed (Recipient A completed their rating)

## UAT-9: Bug fix verification — helper function REVOKE

**Given** an unauthenticated (anon) client
**When** it calls `_is_letter_sender` or `_is_letter_receiver` via PostgREST
**Then** the call fails with permission denied (functions revoked from public/anon)

## UAT-10: Bug fix verification — duplicate delivery constraint

**Given** a letter with an existing delivery to "jan@example.com"
**When** `seal_and_send_letter` attempts to add another delivery to the same "jan@example.com"
**Then** the duplicate is silently skipped (ON CONFLICT DO NOTHING) or rejected

## UAT-11: Bug fix verification — email redaction

**Given** a valid delivery token
**When** `get_letter_by_token` or `get_letter_for_reading` is called
**Then** the response does NOT contain the `receiver_email` field
