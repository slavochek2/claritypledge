# P858 UAT — Event-Driven Transcription (prod-observation scenarios)

> These scenarios CANNOT be CI-automated. They require a real GPU deploy, real GCP
> billing, real Cloud Tasks / Cloud Run behavior, and real wall-clock time. Each is a
> Given/When/Then with a concrete verification method (gcloud / billing console / curl / SQL).
> Run after `/dev` ships the code path + the migration is applied on prod.

**Prod refs:** GPU project `gen-lang-client-0869694595`; Cloud Run `transcribe-session` (us-east4);
Supabase prod `besjtuodziykmjidubzw`. Read-only DB queries via curl + service-role key (this
table's anon read returns `[]`). Mutations require explicit confirmation.

## UAT-0 — Keepalive disproof experiment (PREREQUISITE — RUN FIRST)

Decision 3 leaves the exact keepalive wiring (option a vs b) to be verified against live
Cloud Run + Cloud Tasks behavior. Everything else depends on the answer, so run this first.

- **Given** a stub `/transcribe-async` deployed that sleeps 20 minutes then returns 200,
  and a Cloud Tasks queue with a **30s dispatch deadline**.
- **When** a task is enqueued targeting the stub.
- **Then** observe whether Cloud Tasks marks the task failed + retries (→ option b required:
  202-immediately + separate self-issued keepalive request) OR delivered (→ option a works:
  the target may return early while processing continues under request timeout 3600s).
- **Verify:**
  - `gcloud tasks list --queue=<queue> --location=<loc>` — watch the task's `dispatchCount`/state.
  - Cloud Run logs: `gcloud run services logs read transcribe-session --region=us-east4 --limit=100`
    — did the 20-min stub run to completion on one instance, or was it reclaimed mid-sleep?
- **Pass:** the chosen option (a/b) is confirmed by observation, NOT assumed. Record which.

## UAT-1 — 24h idle → 0 instances + €0 billing (scale-to-zero realized)

- **Given** no `transcription_jobs` inserts for a 24h window and `transcribe-poll` disabled.
- **When** 24h elapse with an empty queue.
- **Then** Cloud Run shows 0 instances the whole window and GPU billing ≈ €0.
- **Verify:**
  - `gcloud run services describe transcribe-session --region=us-east4 --format='value(status.traffic)'`
    and the Metrics tab (instance count) — confirm 0 instances across 24h.
  - Billing console → GPU project → filter `transcribe-session` SKU over the window → ≈ €0.
- **Pass:** instance count is 0 for the full window AND GPU line item ≈ €0. (This is THE fix:
  the old path held €659/mo gross at 0 jobs; this confirms it no longer does.)

## UAT-2 — Concurrency = 1 → 5 simultaneous jobs spin 5 distinct instances; 6th queues

- **Given** Cloud Run `--concurrency=1`, `maxScale=5`, quota=5, Cloud Tasks `maxConcurrentDispatches=5`.
- **When** 6 `transcription_jobs` rows are inserted within seconds of each other.
- **Then** 5 distinct L4 instances start (one job each); the 6th is held by Cloud Tasks until a
  slot frees, then runs — none lost.
- **Verify:**
  - Cloud Run Metrics → instance count peaks at exactly 5 (not 1 packed, not 6).
  - `gcloud tasks list --queue=<queue> --location=<loc>` — the 6th task shows as pending while 5 dispatch.
  - SQL: all 6 jobs reach `completed` (none stuck `pending`/`failed`):
    `curl '.../transcription_jobs?select=id,status&id=in.(<6 ids>)' -H "apikey: <svc>" -H "Authorization: Bearer <svc>"`
- **Pass:** instance peak = 5, 6th queues-then-completes, all 6 `completed`.

## UAT-7 — Auth: tokenless direct call rejected (401/403)

- **Given** `transcribe-session` deployed `--no-allow-unauthenticated` (confirm via
  `gcloud run services describe transcribe-session --region=us-east4 --format='value(...)'`).
- **When** an unauthenticated `curl` hits `/transcribe-async` and `/sweep` (no OIDC token).
- **Then** Cloud Run rejects with 401/403 before any GPU spin.
- **Verify:** `curl -i https://<service-url>/transcribe-async -d '{"job_id":"x"}'` → 401/403;
  repeat for `/sweep`. Confirm no instance started (Cloud Run Metrics flat).
- **Pass:** both endpoints reject tokenless calls; no GPU wakes. (This is THE denial-of-wallet
  must-fix — Security mitigation #1.)

## UAT-11 — Two dispatchers, one job, no double-process (TRUE atomicity — prod observation)

> The unit tests CANNOT prove Postgres-level `FOR UPDATE SKIP LOCKED` atomicity with a mock.
> This is where it is actually verified.

- **Given** a single `pending` job and both the trigger AND a `tx-job-janitor` cycle racing for it
  (engineer the overlap: enqueue the trigger task at the same time a manual `/sweep` runs).
- **When** both dispatchers attempt to claim the same `job_id` simultaneously.
- **Then** exactly ONE wins the claim and processes; the other gets `claimed:false` and spins no GPU.
- **Verify:** exactly ONE `session_transcripts` row for the session (no duplicate); `attempts`
  incremented once; Cloud Run logs show one processing run, the other a `claimed:false` no-op;
  instance count peaks at 1 (not 2).
- **Pass:** one transcript, one increment, one GPU spin. (Falsify-before-rely: this is the
  guarantee asserted in code via the conditional UPDATE; here it is confirmed against real Postgres.)
