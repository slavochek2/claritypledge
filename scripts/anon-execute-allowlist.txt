# Deliberately anon-executable functions (P1064) — read by P1065's grant drift check
#
# Format:  function_signature      # reason — call site file:line
#
# The signature is `pg_proc.oid::regprocedure::text` for a function in schema
# `public`, i.e. `name(argtype,argtype)` with no schema prefix. Overloads are
# distinct entries; they are separately granted and must be separately justified.
#
# WHAT AN ENTRY MEANS
#   "An unauthenticated caller reaching this function is the product working."
#   It does NOT mean the function was audited defect-free, and it does not
#   bless the function's body. It answers one question only: is the anon
#   EXECUTE grant deliberate. Body defects are tracked as their own specs.
#
# RULES FOR ADDING AN ENTRY
#   1. Cite a REAL anon call site as file:line, found by grep — a path that
#      runs before any session exists, or one the code does not gate on a
#      logged-in user. An entry justified by reasoning ("this looks like a
#      guest path") is exactly the entry this check would then bless forever.
#   2. If no such call site exists, the entry does not belong here — whatever
#      the signature suggests. Several functions carry an anon grant that no
#      anon caller uses; those are backlog, not allowlist.
#   3. A token parameter is NOT authorization. A token in a signature is
#      reachability — it says an unauthenticated party can arrive, never that
#      arriving is permitted. Do not let a token end the analysis
#      (docs/decisions.md 2026-08-13 [technical]).
#   4. One line, one reason, product-level. If the reason needs the mechanism
#      of a defect to make sense, it is not a reason for this file.
#
# The check being red is the check working. An unlisted anon-executable
# function is a question to answer, not noise to suppress.
